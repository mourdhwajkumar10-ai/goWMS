# GRN (Goods Receipt Note) Process — WMS Specification

## 1. Purpose

This document defines the proposed GRN / inward receiving workflow for the WMS.

The GRN process must support two inbound shipment modes:

1. **Packing List Mode** — the system knows which items are expected in which box.
2. **Invoice-Only Mode** — the system knows the expected items and quantities from invoices, but does not know which item is in which box.

The operational principle is:

> **Keep normal receiving extremely fast. Operators should primarily scan. Exceptions, reconciliation, audits, and management controls should not unnecessarily interrupt normal scanning.**

---

# 2. High-Level Workflow

```text
TRUCK ARRIVES
     ↓
TRUCK ARRIVAL / CREATE GRN
     ↓
IMPORT PACKING LIST OR ASSIGN INVOICES
     ↓
BOX RECEIVING
     ↓
BOX RECONCILIATION + POD
     ↓
ITEM VERIFICATION
     ├── Packing List Mode
     │      Scan Box → Scan Items → Auto-close if perfect
     │
     └── Invoice-Only Mode
            Consolidated Material → Scan Items
     ↓
EXCEPTIONS / DISCREPANCIES
     ↓
AUDIT (if required)
     ↓
ITEM VERIFICATION COMPLETE
     ↓
PUT-AWAY
     ↓
GRN COMPLETE
     ↓
STOCK AVAILABLE
```

**Put-Away is intentionally left for a later design discussion.**

---

# 3. Receiving Modes

## 3.1 Packing List Mode

Used when the supplier provides a packing list containing box-to-item mapping.

Example:

| Invoice | Box | Part No. | Expected Qty |
|---|---|---|---:|
| INV-001 | BOX-001 | 12345 | 20 |
| INV-001 | BOX-001 | 67890 | 10 |
| INV-001 | BOX-002 | 12345 | 15 |
| INV-001 | BOX-002 | 45678 | 5 |

The system therefore knows:

- Which boxes are expected.
- Which invoice each box/item belongs to.
- Which items are expected in each box.
- Expected quantity per item per box.

This allows true **box-level verification**.

---

## 3.2 Invoice-Only Mode

Used when only invoices are available.

Example:

| Invoice | Part No. | Expected Qty |
|---|---|---:|
| INV-001 | 12345 | 100 |
| INV-001 | 67890 | 50 |
| INV-001 | 45678 | 25 |

The system knows the expected total quantity per item, but does not know which box contains which item.

Therefore:

- Boxes are received/count-verified separately.
- Item verification is performed on the consolidated material.
- Short/excess can be identified at invoice/part level.
- Box-level item attribution is not possible because the source data does not provide it.

---

# 4. Step 1 — Truck Arrival

When the truck arrives, the operator creates the inbound receipt.

### Information captured

- Supplier
- Truck number
- Driver details, if required
- Arrival date/time
- Number of boxes/containers
- Incoming invoices
- Packing list availability
- Receiving mode
- Supporting documents

### Initial status

```text
GRN Status: RECEIVING
```

The system creates a GRN identifier.

Example:

```text
GRN-001245
```

---

# 5. Step 2 — Create / Import GRN

## Packing List Mode

The packing list is imported into the system, for example through XLSX/CSV.

The imported structure should contain at least:

```text
Invoice
Box No.
Part No.
Quantity
```

The system validates the import and associates the expected contents with the GRN.

Incoming invoices are assigned to the GRN.

---

## Invoice-Only Mode

Invoices are assigned to the GRN.

The system creates the expected item/quantity structure from the invoice data.

No box-to-item mapping is created.

---

# 6. Step 3 — Box Receiving

Box receiving happens before the boxes are opened for item verification.

The physical boxes/containers are unloaded into the receiving area.

Each box is scanned.

The box identifier can be:

- Supplier/Bajaj box QR/barcode, where available.
- A QR/barcode generated by the WMS and placed on the box.
- Another approved box identifier.

The operator scans:

```text
BOX-001
BOX-002
BOX-003
...
```

## Important

The box is scanned **once during box receiving** to establish physical receipt.

The box is later scanned again at the beginning of **item verification** in Packing List Mode. This second scan establishes the box context for item verification.

---

# 7. Box Receiving Validation

For each box scan, the system checks the box against the GRN.

## Expected Box

```text
BOX-048
✓ Expected
✓ Received
```

## Duplicate Box

```text
⚠ BOX ALREADY SCANNED
BOX-048
```

The system records the duplicate scan as an event.

## Unexpected / Excess Box

```text
⚠ EXCESS BOX
BOX-127
```

The box should enter an exception state rather than silently becoming accepted stock.

## Missing Box

After box receiving is completed, the system compares expected and received boxes.

Example:

```text
Expected: 126
Received: 124
Missing: 2
```

The system must identify the exact missing boxes.

---

# 8. Step 4 — Box Reconciliation

After all available boxes have been scanned, show a reconciliation screen.

Example:

```text
EXPECTED BOXES       126
RECEIVED BOXES       124
EXCESS BOXES           0
MISSING BOXES           2
```

Detailed table:

| Box | Status |
|---|---|
| BOX-001 | Received |
| BOX-002 | Received |
| BOX-087 | Missing |
| BOX-102 | Missing |

The operator/supervisor reviews the result.

---

# 9. POD

Once box receiving/reconciliation is complete, the POD can be captured.

The POD should represent the physical box receipt.

The system should retain:

- POD file/image
- Timestamp
- User
- GRN
- Box receipt summary

The system must not represent missing boxes as physically received simply because they appear on the invoice.

---

# 10. Step 5 — Item Verification

After box receiving, the boxes remain in the receiving/verification area.

They are not treated as fully verified stock until item verification and subsequent required steps are completed.

There are two item-verification workflows.

---

# 11. Packing List Item Verification

This is a **box-wise verification process**.

## Operator workflow

```text
SCAN BOX
   ↓
SYSTEM LOADS EXPECTED CONTENTS
   ↓
PHYSICALLY OPEN BOX
   ↓
SCAN ITEMS INSIDE BOX
   ↓
SYSTEM COMPARES SCANS AGAINST BOX CONTENTS
   ↓
NO DISCREPANCY?
   ├── YES → AUTO-CLOSE BOX → READY FOR NEXT BOX
   └── NO  → KEEP BOX OPEN → EXCEPTION
```

---

## 11.1 Scan Box

The operator must physically scan the box.

Example:

```text
BOX-048
```

The system loads the expected contents of BOX-048.

Example:

| Part No. | Expected |
|---|---:|
| 12345 | 20 |
| 67890 | 10 |
| 45678 | 5 |

The operator physically opens BOX-048.

---

## 11.2 Scan Items

The operator scans each item inside the box.

Only items need to be scanned after the box is identified.

Example:

```text
12345
12345
12345
...
67890
67890
45678
```

Every item scan is automatically associated with:

```text
GRN
→ Invoice
→ Box
→ Part
→ Quantity
→ User
→ Device
→ Timestamp
```

No manual box selection is required.

---

# 12. Automatic Clean Box Closure

If all expected quantities are matched and there are no discrepancies, the box should automatically close.

Example:

| Part | Expected | Scanned | Status |
|---|---:|---:|---|
| 12345 | 20 | 20 | ✓ |
| 67890 | 10 | 10 | ✓ |
| 45678 | 5 | 5 | ✓ |

System result:

```text
BOX-048 ✓ VERIFIED

35 / 35 ITEMS

NO DISCREPANCY

NEXT BOX READY
```

The operator does not need to press a Close Box button.

The scanner immediately becomes ready to scan the next box.

This is a key speed optimization.

---

# 13. Same Item in Multiple Boxes

The system must support the same part appearing in multiple boxes.

Example:

| Box | Part | Expected |
|---|---|---:|
| BOX-001 | 12345 | 20 |
| BOX-002 | 12345 | 15 |
| BOX-003 | 12345 | 25 |

Each box is verified independently.

Final part-level reconciliation:

```text
12345

BOX-001 → 20 / 20 ✓
BOX-002 → 15 / 15 ✓
BOX-003 → 25 / 25 ✓

TOTAL → 60 / 60 ✓
```

This provides both:

- Box-level traceability.
- Part-level reconciliation.

---

# 14. Shortage During Packing List Verification

Example:

```text
BOX-048
Part 12345
Expected: 20
Scanned: 18
Short: 2
```

The box must not automatically close as a clean box.

The discrepancy should be recorded as:

```text
GRN
→ Invoice
→ BOX-048
→ Part 12345
→ Expected 20
→ Received 18
→ Short 2
```

The box remains in an exception state until the discrepancy is handled according to the configured resolution process.

---

# 15. Excess During Packing List Verification

Example:

```text
Part 12345
Expected: 20
Scanned: 21
Excess: +1
```

The system should immediately identify the excess.

The excess should not silently become accepted stock.

It should create an exception requiring verification/resolution.

Possible causes include:

- Genuine supplier excess.
- Duplicate scan.
- Wrong item.
- Employee scanning error.
- Physical counting issue.

---

# 16. Wrong Item During Packing List Verification

Suppose BOX-048 expects:

```text
12345
67890
45678
```

but the employee scans:

```text
99999
```

The system should show:

```text
⚠ WRONG ITEM

Scanned: 99999

This item is not expected in BOX-048.
```

The scan should be recorded as an event.

The item should not silently become accepted against the box.

---

# 17. Invoice-Only Item Verification

In Invoice-Only Mode, there is no box-to-item mapping.

Therefore the item verification process is consolidated.

Workflow:

```text
BOX RECEIVING COMPLETE
        ↓
MATERIAL CONSOLIDATED
        ↓
SCAN ITEMS
        ↓
COMPARE AGAINST INVOICE EXPECTED QUANTITY
        ↓
RECONCILE SHORT / EXCESS
```

Example:

| Part | Expected | Scanned | Difference |
|---|---:|---:|---:|
| 12345 | 100 | 100 | 0 |
| 67890 | 50 | 48 | -2 |
| 45678 | 25 | 27 | +2 |

The system can identify part-level differences, but cannot identify which box contained the shortage/excess because the packing-list mapping was unavailable.

---

# 18. Exception Handling

Exceptions should not unnecessarily interrupt normal scanning.

Normal operation should remain:

```text
SCAN → FEEDBACK → NEXT SCAN
```

Exceptions should be collected for review.

### Exception types

- Shortage
- Excess
- Wrong item
- Duplicate scan
- Unexpected box
- Missing box
- Other receiving discrepancy

Each exception should have:

```text
GRN
Invoice
Box (where applicable)
Part
Expected Qty
Scanned/Received Qty
Variance
User
Device
Timestamp
Status
Resolution
Resolved By
Resolution Timestamp
```

---

# 19. Duplicate Scan / Employee Error

The system records every scan event.

However, a scan log alone cannot prove whether a physical item was scanned twice.

Example:

```text
Expected: 20
Scan events: 20
Physical count later: 19
```

The system knows that 20 scan events occurred, but physical audit is required to determine the actual reason for the discrepancy.

This is why the audit capability is important.

---

# 20. Audit

An audit option should be available for selected/random items.

Example:

```text
AUDIT

Random:
5 items
10 items
20 items
Custom

[ START AUDIT ]
```

The system selects items for physical verification.

Example:

```text
Part: 12345

System Qty: 20
Physical Qty: 20

✓ PASS
```

Or:

```text
Part: 12345

System Qty: 20
Physical Qty: 18

⚠ FAIL
```

Audit actions must also be recorded as events.

---

# 21. Follow-Up Receipt

A missing/short material delivery later should be linked to the original GRN.

Example:

Original:

```text
GRN-001245
BOX-087
Part 12345
Expected: 20
Received: 0
Short: 20
```

Later supplier sends the material.

The operator creates:

```text
FOLLOW-UP RECEIPT
        ↓
LINK TO GRN-001245
        ↓
BOX-087
        ↓
SCAN / VERIFY MATERIAL
        ↓
RECONCILE ORIGINAL SHORTAGE
```

Final result:

```text
Original:
20 Expected
0 Received
20 Short

Follow-up:
20 Received

Final:
20 Expected
20 Received
0 Outstanding
```

This maintains a continuous history rather than creating an unrelated receipt.

---

# 22. Event Log

The WMS should capture an event for every scan and every important GRN action.

Examples:

```text
TRUCK_CREATED
GRN_CREATED
INVOICE_ASSIGNED
PACKING_LIST_IMPORTED

BOX_SCANNED
BOX_RECEIVED
BOX_DUPLICATE_SCANNED
BOX_EXCESS_DETECTED

ITEM_SCANNED
ITEM_WRONG_SCANNED
ITEM_EXCESS_DETECTED
ITEM_SHORT_RECORDED

BOX_AUTO_VERIFIED
BOX_CLOSED
EXCEPTION_CREATED
EXCEPTION_RESOLVED

AUDIT_STARTED
AUDIT_ITEM_CHECKED
AUDIT_DISCREPANCY_FOUND

FOLLOWUP_RECEIPT_CREATED
FOLLOWUP_ITEM_RECEIVED

PUTAWAY_STARTED
PUTAWAY_COMPLETED

GRN_COMPLETED
```

## Event fields

Each event should capture appropriate context, including:

```text
Event ID
Event Type
Timestamp
User
Device
GRN
Invoice
Box
Part
Quantity
Result
Reason / Exception
```

Events should be immutable.

The system should maintain:

> **Event History = what happened**

and separately:

> **Current State = what the GRN/box/item looks like now**

Historical events should not be overwritten.

# 23. GRN Status / Workflow States

Suggested high-level states:

```text
DRAFT
   ↓
RECEIVING
   ↓
BOX_RECONCILIATION
   ↓
ITEM_VERIFICATION
   ↓
EXCEPTION_PENDING (if applicable)
   ↓
ITEM_VERIFICATION_COMPLETE
   ↓
PUTAWAY_PENDING
   ↓
PUTAWAY_IN_PROGRESS
   ↓
COMPLETED
```

For the two receiving modes, the item-verification behavior differs, but the overall GRN lifecycle remains the same.

# 25. Operator vs Supervisor Experience

## Operator

The operator should mostly experience:

```text
SCAN
 ↓
SYSTEM FEEDBACK
 ↓
NEXT SCAN
```

They should not have to manually enter:

- GRN numbers
- Box numbers
- Part numbers
- Quantities, where scan-based verification can determine them
- Reconciliation calculations

---

## Supervisor

The supervisor gets access to:

- Reconciliation
- Exceptions
- Audit
- Follow-up receipts
- Activity/Event Log
- GRN history

This keeps the operator experience fast while retaining strong controls.

# 28. Core Design Principles

1. **Scan-first operation** — minimize typing and clicking.
2. **Box-level traceability** wherever packing-list data exists.
3. **Part-level reconciliation** for the entire GRN.
4. **No silent acceptance of discrepancies.**
5. **Clean boxes auto-close.**
6. **Exceptions are isolated from normal scanning.**
7. **Every scan is logged as an event.**
8. **Events are immutable.**
9. **Audit can independently verify physical quantities.**
10. **Follow-up receipts remain linked to the original shortage.**
11. **Operator screens stay simple; supervisor controls stay detailed.**
12. **Put-away remains a separate downstream process and will be designed separately.**
